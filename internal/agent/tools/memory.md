Remember durable facts across conversations, or recall what was remembered before.

<usage_notes>
- Memory is for knowledge that should outlive this session: architecture decisions and their
  rationale, project conventions, environment quirks, commands that work, and gotchas you
  had to discover the hard way.
- Do NOT store: the current task's progress, a restatement of the user's last message, or
  anything you can re-derive by reading the repository. Those belong in the todo list or
  simply in the conversation.
- One note per durable fact, with a stable `name`, so a later correction overwrites the old
  note instead of accumulating contradictions. Rewriting a note with the same name is normal
  and expected when you learn something better.
- `search` before writing: if a note on the subject already exists, update it rather than
  creating a near-duplicate. Search also answers "what do we already know about this".
- Keep bodies short and concrete. Prefer file paths, symbol names and exact commands over
  prose description.
- When a stored memory turns out to be wrong, overwrite it with the correction and say what
  changed. A stale note is worse than no note.
</usage_notes>
